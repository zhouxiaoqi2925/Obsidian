# 架构模式对比

## 模式总览

| 模式 | 特点 | 适用场景 | 核心优势 | 潜在风险 |
|------|------|----------|----------|----------|
| **单体架构** | 单一容器统一部署 | 简单应用、MVP | 成本低、性能高、简单 | 扩展性差 |
| **微服务架构** | 独立服务分布式 | 现代复杂应用 | 便于更新测试、独立扩展 | 复杂度高、运维难 |
| **客户端-服务器** | 请求-响应模型 | 邮件、网站、API | 适合交互式服务 | 单点风险 |
| **分层架构** | 多层职责分离 | 企业应用、电商 | 最广泛使用、分层清晰 | 层间通信开销 |
| **事件驱动架构** | 实时事件处理 | 高交互场景 | 响应快、松耦合 | 调试复杂、事件顺序 |

## 单体架构 (Monolithic)

### 特点
- 单一容器包含所有组件
- 共享代码库，统一部署
- 所有功能打包为一个整体

### 适用场景
- 小型应用、MVP 原型
- 团队规模小（<5人）
- 复杂度低、需求稳定

### 架构示意
```
┌─────────────────────────────────────────┐
│           单体应用容器                   │
│  ┌─────────┬─────────┬─────────┐       │
│  │ 表现层  │ 业务层  │  数据层  │       │
│  └─────────┴─────────┴─────────┘       │
│              ↓                           │
│         统一部署                         │
└─────────────────────────────────────────┘
```

### 优点
- ✅ 开发、测试、部署简单
- ✅ 性能高（无网络开销）
- ✅ 成本低（无需分布式基础设施）

### 缺点
- ❌ 扩展性有限（只能整体扩展）
- ❌ 更新需整体重新部署
- ❌ 技术栈固定（难以局部升级）
- ❌ 故障影响整个系统

---

## 微服务架构 (Microservices)

### 特点
- 拆分为小型独立服务
- 每个服务有独立代码库
- 服务间通过 API 通信
- 可独立部署和扩展

### 适用场景
- 大型复杂应用
- 多团队协作
- 高可用要求
- 持续交付

### 架构示意
```
┌─────────┐  ┌─────────┐  ┌─────────┐
│ 用户服务 │  │ 订单服务 │  │ 支付服务 │
└────┬────┘  └────┬────┘  └────┬────┘
     │            │            │
     └────────────┼────────────┘
                  ↓
           ┌──────────┐
           │ API Gateway │
           └──────────┘
```

### 优点
- ✅ 独立部署（单个服务可更新）
- ✅ 独立扩展（按需扩展瓶颈服务）
- ✅ 技术多样性（不同服务可用不同栈）
- ✅ 容错性（单服务故障不影响全局）

### 缺点
- ❌ 复杂度高（分布式系统挑战）
- ❌ 运维难（需要服务发现、监控、追踪）
- ❌ 网络开销（API调用有延迟）
- ❌ 数据一致性（分布式事务难处理）

---

## 客户端-服务器架构 (Client-Server)

### 特点
- 客户端发送请求
- 服务器处理请求并返回资源
- 典型的请求-响应模型

### 适用场景
- 邮件服务
- 网站应用
- 文件共享
- API 服务

### 架构示意
```
┌─────────┐          ┌─────────┐
│  客户端  │ ←──────→ │  服务器  │
│ (用户)   │  请求    │ (处理)  │
└─────────┘  ←──────→ └─────────┘
```

### 优点
- ✅ 适合交互式服务
- ✅ 集中管理数据和业务逻辑
- ✅ 易于权限控制

### 缺点
- ❌ 单点故障风险
- ❌ 服务器性能成为瓶颈
- ❌ 客户端需要安装

---

## 分层架构 (Layered / N-tier)

### 特点
- 将应用分为多个层级
- 每层只与相邻层通信
- 职责分明、模块化

### 适用场景
- 企业应用（最广泛使用）
- 电商平台
- 后台管理系统

### 架构示意
```
┌─────────────────────────────┐
│     表现层 (Presentation)    │ ← 用户界面
├─────────────────────────────┤
│       业务层 (Business)      │ ← 业务逻辑
├─────────────────────────────┤
│      应用层 (Application)    │ ← 服务编排
├─────────────────────────────┤
│       数据层 (Data)           │ ← 数据库
└─────────────────────────────┘
        ↓ 只能与相邻层通信 ↓
```

### 各层职责

| 层级 | 职责 | 示例 |
|------|------|------|
| 表现层 | 用户界面渲染 | HTML/CSS/UI组件 |
| 业务层 | 核心业务逻辑 | 订单处理、计算规则 |
| 应用层 | 服务编排协调 | 工作流、事务管理 |
| 数据层 | 数据持久化 | SQL/NoSQL、文件系统 |

### 优点
- ✅ 开发、测试、维护简化
- ✅ 层可独立更新（不影响其他层）
- ✅ 职责清晰、易于理解
- ✅ 可替换层实现（如换数据库）

### 缺点
- ❌ 层间通信开销
- ❌ 可能导致分层过深
- ❌ 所有请求必须穿过所有层

---

## 事件驱动架构 (Event-driven)

### 特点
- 以事件为核心
- 事件生产者 → 事件路由 → 消费者
- 松耦合、实时响应

### 适用场景
- 高交互电商（注册表单、购物车）
- 实时通知系统
- 物联网数据处理
- 金融交易系统

### 架构示意
```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ 事件生产者    │ → │   事件路由    │ → │  事件消费者   │
│ (用户操作)    │    │ (Kafka等)    │    │ (处理逻辑)   │
└──────────────┘    └──────────────┘    └──────────────┘
      ↓
  用户点击"加入购物车"
      ↓
  实时处理响应
```

### 优点
- ✅ 松耦合（生产者和消费者独立）
- ✅ 实时响应（事件触发即时处理）
- ✅ 可扩展（添加消费者不影响系统）
- ✅ 可审计（事件日志完整）

### 缺点
- ❌ 调试复杂（异步流程难追踪）
- ❌ 事件顺序（需处理乱序问题）
- ❌ 幂等性（重复事件处理）
- ❌ 最终一致性（不是强一致）

## 架构选型决策树

```
项目复杂度
     │
     ├── 低（简单应用、MVP）
     │        ↓
     │     【单体架构】
     │     快速开发、低成本
     │
     ├── 中等（企业应用、电商）
     │        ↓
     │     【分层架构】
     │     职责清晰、易维护
     │
     └── 高（现代复杂系统）
              ↓
           ┌─────────────────┐
           ↓                 ↓
     【微服务】        【事件驱动】
     独立部署         高交互实时
     团队协作         松耦合
```

## 选择建议

| 场景 | 推荐架构 |
|------|----------|
| 创业MVP快速验证 | 单体 |
| 企业后台系统 | 分层 |
| 电商平台 | 分层 + 事件驱动 |
| 流媒体/社交 | 微服务 |
| 金融交易系统 | 事件驱动 |
| 物联网数据处理 | 事件驱动 |
