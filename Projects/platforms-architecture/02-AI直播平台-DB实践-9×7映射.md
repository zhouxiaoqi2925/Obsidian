### 🔧 MVP 阶段 9×7 实战清单(7 列)

#### A 列(结构)
- [ ] 用户/订单/商品/直播间 4 张核心表建表(A1-A4)
- [ ] `BIGSERIAL PRIMARY KEY` 主键策略统一
- [ ] `NUMERIC(20,4)` 财务字段精度锁死
- [ ] `TIMESTAMPTZ` 全时间字段带时区

#### B 列(逻辑)
- [ ] 所有写 SQL 走 `BEGIN; ... COMMIT;` 短事务
- [ ] 库存扣减用 `FOR UPDATE` + 短事务(< 100ms)
- [ ] 弹幕写入 Redis Stream 而非 PG
- [ ] 慢 SQL 走 `pg_stat_statements` 监控

#### C 列(配置)
- [ ] 核心查询建 B-Tree 复合索引
- [ ] 商品 JSONB 属性建 GIN 索引
- [ ] 时序大表(直播事件)建 BRIN 索引
- [ ] `random_page_cost = 1.1` (SSD 调优)

#### D 列(用例)
- [ ] pgTAP 覆盖 4 张核心表(插入/更新/删除/约束)
- [ ] pgbench 压测:32 并发 60s,记录基线 TPS
- [ ] 关键接口压测:登录/开播/下单/支付

#### E 列(校验)
- [ ] ER 图 Mermaid 落地:`USERS / ORDERS / LIVE_ROOMS / PRODUCTS`
- [ ] 业务主键与物理主键分离(`id BIGSERIAL` + `biz_id VARCHAR`)
- [ ] 状态机:`orders.status` 1=待支付 2=已支付 3=已发货 4=已完成 5=退款
- [ ] CHECK 约束:`balance >= 0`、`status IN (...)`

#### F 列(指标)
- [ ] pg_exporter + Prometheus + Grafana 三件套
- [ ] QPS / TPS / 慢查询 / 死锁 4 仪表盘
- [ ] 告警:P99 > 200ms / 连接数 > 80% / 死锁 > 0
- [ ] 每日巡检脚本:bloat / 索引命中率 / 复制延迟

#### G 列(规则)
- [ ] 3 角色:`openlive_app` / `openlive_readonly` / `openlive_audit`
- [ ] 最小权限:app 只能 SELECT/INSERT/UPDATE/DELETE,无 DDL
- [ ] 密码 90 天轮换 + `VALID UNTIL`
- [ ] pgaudit 开启,记录所有写操作

### 🔧 规模化阶段 9×7 实战清单

#### A 列
- [ ] 用户表按 `user_id % 16` 水平分 16 库 64 表
- [ ] 订单表按 `user_id` 分 + 按 `created_at` 分月归档
- [ ] 商品表按 `category_id` 范围分区
- [ ] 历史数据冷热分离:1 年前数据走 OSS + 列存

#### B 列
- [ ] 分布式事务:下单→扣库存→扣款 Saga 编排
- [ ] 跨库 JOIN 禁止,改走 `WHERE user_id IN (...)` 多次查询合并
- [ ] 全局唯一 ID:雪花算法(Snowflake)64bit
- [ ] `pg_cron` 定时清理过期数据 + 归档

#### C 列
- [ ] Elasticsearch 双索引:近实时 + 历史
- [ ] 异步写入 Kafka → ES(弹幕/评论不阻塞主库)
- [ ] 读路径:Redis 缓存(短)→ ES 全文(中)→ PG 实时(长)
- [ ] 预计算:MV 物化视图 + 定时刷新

#### D 列
- [ ] 混沌演练:节点宕机 / 网络分区 / 磁盘满
- [ ] 故障注入:`tc netem` 加 200ms 延迟 / `dd` 灌满磁盘
- [ ] 回归测试:每次 schema 变更跑 500 条 SQL 回归
- [ ] 性能基线:QPS / P99 / 错误率三指标每版本比对

#### E 列
- [ ] 业务事件溯源(Event Sourcing):订单状态变更全留痕
- [ ] CQRS 读写分离:写主库 + 读从库 + 投影到 ES
- [ ] 业务规则引擎:`orders.status` 转换走规则表驱动
- [ ] 多租户隔离:`tenant_id` 字段 + RLS policy

#### F 列
- [ ] 全链路 TraceID 串联:`pg_stat_statements` + OTel
- [ ] 慢查询阈值 < 100ms(从 200ms 收紧)
- [ ] 容量预估脚本:`growth_rate * 3month = capacity_needed`
- [ ] 自动扩容:CPU > 70% 触发,读副本 +1

#### G 列
- [ ] 敏感字段加密:`email / phone / id_card` AES-256-GCM
- [ ] KMS 密钥管理,30 天轮换
- [ ] 数据脱敏:`pg_dump` 导出生产数据自动脱敏
- [ ] 异地多活:RPO < 5s,RTO < 30s

## 四、AI 直播平台 DB 架构演进路线(总览)

```
Phase 0 MVP              Phase 1 规模化            Phase 2 头部
─────────────           ─────────────            ─────────────
PostgreSQL 16            PostgreSQL → 分库分表      OceanBase 4.x
单实例 → 主从             16 库 64 表              100+ 节点
Redis 单实例              Redis Cluster             Redis 7 + 多 AZ
SQLite (本地)            Elasticsearch             Milvus (向量)
-                        Kafka                     Kafka + Flink
-                        OSS + CDN                 多活 + 边缘
```

### 演进铁律(9×7 视角)
1. **A 列**:从单表 → 分区 → 分库分表 → 单元化(每阶段都是 A3 的递进)
2. **B 列**:从单机事务 → 跨库事务 → Saga → 分布式事务(每阶段都是 B2 的递进)
3. **C 列**:从单索引 → 复合/部分 → 异步索引(ES) → 向量索引(每阶段都是 C1 的递进)
4. **F 列**:从指标采集 → 实时监控 → 全链路追踪 → AIOps(每阶段都是 F1-F4 的递进)

## 四、Phase 4 (零依赖重构·项目实际状态) DB 任务 × 9×7 列映射

> **核心前提**:2026-06-28 用户决策「只进行修改和补齐,不重构不删除」。原 Phase 4 计划的 PostgreSQL 16 / embedded-postgres / SQLite **全部不执行**。
> **项目实际数据架构**(基于 main.py 探索):
> - **进程内 `Dict`**:`users_db` / `sessions` / `danmaku_queue` / `live_history` 等
> - **重启即丢**:无持久化 / 无 WAL / 无 checkpoint
> - **无 ORM**:直接操作 Dict / 列表推导 / dict.get(key, default)
> - **无迁移**:数据结构随 main.py 改而改,无 schema 版本管理
> - **无索引**:Dict 查询是 O(n) 线性扫描(用户量小可接受)
>
> **本节定位**:把"内存 Dict 数据层"作为 DB 视角的实际状态,按 9×7 7 列索引;与 Phase 0-3 的 PostgreSQL 路线并存。

### 4.3 内存 Dict vs PostgreSQL 路线对照

| 维度 | 内存 Dict(当前) | PostgreSQL 16(理想) | 迁移路径 |
|---|---|---|---|
| 持久化 | ❌ 重启丢 | ✅ WAL + checkpoint | 待用户决策 |
| 并发安全 | ⚠️ asyncio.Lock | ✅ MVCC | 加锁即可 |
| 查询能力 | ⚠️ O(n) 全扫 | ✅ B-Tree / GIN / BRIN 索引 | 加 SQL 层 |
| 事务 | ❌ 无 | ✅ ACID | 重写关键路径 |
| 部署 | ✅ 零依赖 | ⚠️ 需外部 PG | PyInstaller 嵌入 |
| 改动量 | 0(当前) | ~2 人天 | 视业务规模 |
| 适用场景 | MVP / 用户 < 1000 | 规模化 / 用户 > 1000 | 渐进迁移 |

> **决策记录**:2026-06-28 用户决策「不引入 SQLite/PG」,理由是项目当前阶段内存 Dict 完全够用,且符合「只修改补齐不重构」原则。**SQLite 是零依赖升级路径(单文件 / 无服务 / 兼容 Dict API)**,若未来需要持久化可优先考虑。
