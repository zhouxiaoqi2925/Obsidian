# 三层横向对比 · 数据库 × 后端 × 前端(9×7 同列不同模块族)

> **核心命题**:同一套 **9 级 × 7 列** 拆解骨架,如何**同时适配**三层(数据库 / 后端 / 前端)?
> **铁律**:7 列业务含义**完全固定**(A结构/B逻辑/C配置/D用例/E校验/F指标/G规则),只允许**对应不同模块族**。
> **价值**:一张表看清「同一指标,在 DB / 后端 / 前端 三层各自意味着什么」,避免技术评审 / Code Review 跨层沟通歧义。

## 十、三层 × 9 级 节点数对比

```
单链路节点数(三层通用) = 1 × 5 × 4 × 4 × 4 × 4 = 1280(七级深度)
单链路节点数(含亚比特) = 1280 × 4 × 4 = 20480(九级深度)
7 列 × 20480 = 143,360 总节点数 / 层

三层合计 = 143,360 × 3 = 430,080 总节点数 / 三大层
```

> **量级提示**:三层合计 **43 万+ 节点**,实际工作中**不需要全部展开**,采用「**关键路径深耕 + 一般路径只到三级**」策略。

## 十二、三层框架的「同与异」本质

### 12.1 相同点(同 9×7 矩阵)

1. **7 列含义固定**:A结构/B逻辑/C配置/D用例/E校验/F指标/G规则,三层通用
2. **9 级深度一致**:一级模块 → 二级子模块 → ... → 九级亚比特
3. **节点量级一致**:每层 14 万+ 节点(七级)
4. **拆解方法一致**:骨架先行 → 填充知识 → 串联 checklist
5. **实战策略一致**:关键路径深耕 + 一般路径只到三级

### 12.2 不同点(不同模块族)

| 差异维度 | 数据库 | 后端 | 前端 |
|---------|-------|-----|-----------|
| **核心实体** | 表 / 字段 | 服务 / 模块 | 组件 / 页面 |
| **核心逻辑** | SQL / 触发器 | Go/Java 代码 | JS/TS 代码 |
| **核心配置** | postgresql.conf | config.yaml | .env + webpack.config |
| **核心测试** | pgTAP | gomock | Vitest |
| **核心指标** | QPS / TPS | P99 / 错误率 | FCP / LCP / CLS |
| **核心规则** | 权限 / 加密 | 鉴权 / 灰度 | 路由守卫 / CSP |
| **部署形态** | 主从 / 集群 | 微服务 / K8s | CDN / 静态托管 |
| **演进方向** | 单库 → 分布式 | 单体 → 微服务 → 单元化 | 单页 → 微前端 |
| **最严苛的延迟** | < 50ms(主键查询) | < 200ms(P99) | < 100ms(交互响应) |
| **最严苛的可用性** | 99.999% | 99.95% | 99.9% |

## 十三、跨层协作铁律(AI 直播平台专项)

### 13.1 字段同源铁律

> **同一字段必须在三层定义一致**:DB 字段类型、长度、约束 ⇔ 后端 VO/Entity 类型 ⇔ 前端 TypeScript 类型。

**反例**(常见 bug):
- DB: `balance NUMERIC(20,4)` ← 4 位小数
- 后端: `float64 balance` ← 浮点丢精度 ❌
- 前端: `number balance` ← 64 位整数安全 ❌

**正例**(三层一致):
- DB: `balance NUMERIC(20,4) NOT NULL CHECK (balance >= 0)`
- 后端: `decimal.Decimal balance` + `binding:"required,gte=0"`
- 前端: `Decimal balance` (decimal.js) + Yup 校验

### 13.2 状态机同源铁律

> **同一状态机必须在三层定义一致**:DB CHECK 枚举 ⇔ 后端状态机库 ⇔ 前端 TS enum。

**AI 直播订单状态**:
- DB: `status SMALLINT CHECK (status IN (1,2,3,4,5))`
- 后端: `OrderStatus enum { Pending=1, Paid=2, Shipped=3, Completed=4, Refunded=5 }`
- 前端: `enum OrderStatus { Pending=1, Paid=2, Shipped=3, Completed=4, Refunded=5 }`

### 13.3 错误码同源铁律

> **同一错误码必须在三层定义一致**:DB 错误码 ⇔ 后端 BizError ⇔ 前端 ErrorCode。

**AI 直播业务错误码**:
- 后端: `BizError{Code: 40001, Msg: "库存不足"}`
- 前端: `ErrorCode 40001 → toast.error("库存不足,请减少购买数量")`
- DB: 触发器 / 约束检查失败抛错码 → 后端捕获映射 → 前端展示

### 13.4 时区同源铁律

> **三层的时区必须统一为 UTC 存储 + 本地展示**。

- DB: `TIMESTAMPTZ` (PG) / `DATETIME` (MySQL)
- 后端: `time.UTC` 存储 / `time.Local` 展示
- 前端: `dayjs.utc()` 接收 / `dayjs.tz.guess()` 展示

### 13.5 版本同源铁律

> **API 版本 / 路由版本 / DB 迁移版本必须联动**。

- DB: Flyway `V20260625_001__add_balance_column.sql`
- 后端: `/api/v1/user/:id` + `Balance` 字段
- 前端: 路由 `/v1/profile` + TS `User.balance` 字段
