## 2. MComplexConnect：多 IP 并发竞速连接

> **MComplexConnect 是视频号"秒开"体验的核心**。在用户点开视频号直播的瞬间，客户端会同时向 4-8 个 CDN 边缘节点的 IP 发起 TCP 连接，谁先连上就用谁。**这是腾讯 Mars 网络库最精妙的设计**。

**源码位置**：`C:\Users\15389\source\Mars\mars\comm\socket\complexconnect.h`（163 行）

### 2.1 类签名


**MComplexConnect 是一个纯虚观察者类**——只有回调，没有状态。设计为 `Observer` 模式，让 `ComplexConnect` 触发事件，业务方实现回调。

**7 个回调**：

| 回调 | 触发时机 | 用途 |
|---|---|---|
| `OnCreated` | socket 创建完成 | 打日志、做 socket option 优化 |
| `OnConnect` | 发起 connect() 系统调用 | 触发 TCP fast open |
| `OnConnected` | 连接成功/失败 | 拿到 RTT（首包延迟） |
| `OnShouldVerify` | 询问是否需要验证 | 业务层做"白名单"判定 |
| `OnVerifySend` | 业务层发送验证包 | TLS 之前做 app 层的 token 验证 |
| `OnVerifyRecv` | 业务层接收验证包 | 收到验证包后校验 |
| `OnVerifyTimeout` | 验证超时 | 强制断开 |
| `OnFinished` | 整个竞速结束 | 拿到最终耗时 `complex_totalcost` |

### 2.3 三个构造函数的不同策略

```cpp
// 第一个：基础版（总超时 + IP 间间隔）
ComplexConnect(unsigned int _timeout, unsigned int _interval);

// 第二个：增加错误 IP 的重试间隔
ComplexConnect(unsigned int _timeout, unsigned int _interval,
               unsigned int _error_interval, unsigned int _max_connect);

// 第三个：IPv4 / IPv6 分别设超时
ComplexConnect(unsigned int _timeout, unsigned int _interval,
               unsigned int _error_interval, unsigned int _v4_timeout, unsigned int _v6_timeout);
```

**3 个构造函数**对应 3 种使用场景：

1. **基础版**——所有 IP 共享同一个 `timeout_`，适用于"全部一视同仁"
2. **错误间隔版**——加 `error_interval_`（错误 IP 不立即重试）和 `max_connect_`（最多并发几个）
3. **IPv4/IPv6 分开**——`v4_timeout_` 和 `v6_timeout_` 可以不同，因为 IPv6 网络下系统调用要慢一些

### 2.4 ConnectImpatient 方法签名

```cpp
SOCKET ConnectImpatient(const std::vector<socket_address>& _vecaddr,
                        SocketBreaker& _breaker,
                        MComplexConnect* _observer = NULL,
                        mars::comm::ProxyType _proxy_type = mars::comm::kProxyNone,
                        const socket_address* _proxy_addr = NULL,
                        const std::string& _proxy_username = "",
                        const std::string& _proxy_pwd = "");
```

**`Impatient`（没耐心的）一词点睛**——这个方法"等不了"，谁先连上用谁。

**参数解读**：

| 参数 | 含义 |
|---|---|
| `_vecaddr` | 所有候选 IP 的 `vector<socket_address>` |
| `_breaker` | 中断开关——可以主动打断整个竞速 |
| `_observer` | 观察者回调（业务方实现） |
| `_proxy_type` | 是否走 HTTP/SOCKS5 代理 |
| `_proxy_addr` | 代理地址 |
| `_proxy_username` | 代理账号 |
| `_proxy_pwd` | 代理密码 |

**返回值 `SOCKET`**——直接返回已连接的 socket（`INVALID_SOCKET` 表示失败）。**这是底层的 fd，业务方拿这个 fd 直接 read/write**。

### 2.5 状态查询方法

```cpp
unsigned int TryCount() const { return trycount_; }  // 试了几个 IP
int Index() const { return index_; }                  // 最终用了第几个 IP
int ErrorCode() const { return errcode_; }            // 错误码

```

**为什么会有 `TryCount()` 和 `TotalCost()`？** 业务方在 `OnFinished` 回调里用这些数据做监控：

- 试了几个 IP（`trycount_`）→ 监控"用户所在网络有没有可用 IP"
- 总耗时（`totalcost_`）→ 监控"秒开体验"
- 中断率（`is_interrupted_`）→ 监控"用户取消率"

### 2.6 `__ConnectTime` 和 `__ConnectTimeout` 私有方法


**两个虚函数式多态方法**——根据 `_index` 返回该 IP 当前的"已经过时间"和"剩余超时时间"。

## 3. SocketBreaker：socket 操作的"急停开关"

> **SocketBreaker 是 Mars 实现"可取消 socket"的核心**。它的设计精妙到只用一对 pipe（无名管道）就实现了"跨线程中断正在阻塞的 socket 操作"。

**源码位置**：`C:\Users\15389\source\Mars\mars\comm\unix\socket\socketbreaker.h`（64 行）

### 3.1 类签名

```cpp
// C:\Users\15389\source\Mars\mars\comm\unix\socket\socketbreaker.h:25-58
class SocketBreaker {
 public:
    SocketBreaker();
    ~SocketBreaker();

    bool IsCreateSuc() const;
    bool ReCreate();
    void Close();

    bool Break();
    bool Break(int reason);
    bool Clear();
    bool PreciseBreak(uint32_t cookie);
    bool PreciseClear(uint32_t* cookie);

    bool IsBreak() const;
    int BreakerFD() const;
    int BreakReason() const;

 private:
    SocketBreaker(const SocketBreaker&);
    SocketBreaker& operator=(const SocketBreaker&);
    void _Cleanup();

 private:
    int pipes_[2];
    bool create_success_ = false;
    bool breaked_ = false;
    int reason_ = 0;
    mutable std::mutex mutex_;
};
```

### 3.2 核心设计：pipe + mutex

```cpp
private:
    int pipes_[2];                  // ⭐ 关键：一对 pipe fd
    bool create_success_ = false;   // pipe 创建成功？
    bool breaked_ = false;          // 是否已经 break
    int reason_ = 0;                // break 原因
    mutable std::mutex mutex_;      // 线程安全
```

**`pipes_[2]`**——一个匿名管道（`pipe(pipes_)`）。`pipes_[0]` 是读端，`pipes_[1]` 是写端。

### 3.3 工作原理

**Break 流程**（`Break()` 方法）：

```cpp
// 伪代码
bool Break() {
    std::lock_guard<std::mutex> lock(mutex_);
    if (!create_success_) return false;
    if (breaked_) return true;  // 已 break 不重复
    
    // 关键：向 pipe 写一个字节
    char c = 0;
    write(pipes_[1], &c, 1);
    breaked_ = true;
    return true;
}
```

**读取端如何感知 Break**：

业务方在 `select/poll/epoll` 时把 `pipes_[0]`（`BreakerFD()`）也加入监听：

```cpp
// 视频号推流线程
int fd_to_watch[2] = { rtmp_socket, breaker.BreakerFD() };
while (!breaker.IsBreak()) {
    poll(fd_to_watch, 2, 1000 /*ms*/);
    
    if (fd_to_watch[1] & POLLIN) {
        // breaker 触发了！
        char c;
        read(breaker.BreakerFD(), &c, 1);
        break;
    }
    
    // 处理 rtmp_socket 的事件
    ...
}
```

**这就是经典"self-pipe trick"**——POSIX 下用 pipe 实现可中断 IO。

### 3.4 三个层级的 Break

```cpp
bool Break();                        // 普通 break
bool Break(int reason);              // 带原因的 break
bool PreciseBreak(uint32_t cookie);  // 精确 break：只有匹配的 cookie 才能 clear
```

**`PreciseBreak / PreciseClear` 的设计场景**：

```cpp
// 场景：1 个连接上有 3 个请求并发
uint32_t cookie1 = 1, cookie2 = 2, cookie3 = 3;
breaker.PreciseBreak(cookie2);  // 只 cancel 第 2 个请求

// 业务方在第 2 个请求的回调里
if (breaker.PreciseClear(&cookie2)) {
    // 我是被 cancel 的那个
    return;
}
```

### 3.5 IsBreak 与 BreakReason

```cpp
bool IsBreak() const;       // 当前是否已 break
int BreakReason() const;    // break 的原因
int BreakerFD() const;      // 暴露给 poll/epoll 的读端 fd
```

**`BreakerFD()` 是整个设计的灵魂**——它把"中断"变成了"可被 poll 的事件"。

## 4. SocketPoll：epoll/kqueue 跨平台封装

> **SocketPoll 是 Mars 的 IO 多路复用底层**。Linux 用 epoll，macOS/iOS 用 kqueue，Windows 用 IOCP——Mars 把这些差异封装成统一的 poll 接口。

**源码位置**：`C:\Users\15389\source\Mars\mars\comm\unix\socket\socketpoll.h`

### 4.1 设计哲学

**不要在 UI 线程做 IO**——视频号推流、播放、心跳全部走独立线程，每个线程用 `SocketPoll` 监听一组 socket。

```
┌──────────────────────────────────────────────────┐
│                 视频号进程                          │
│                                                    │
│  UI 线程 (主)                                       │
│  ├─ 视频解码 (SurfaceView/MediaCodec)              │
│  └─ 渲染                                            │
```

## 9. MMKV：mmap + protobuf 的零拷贝 KV

> **MMKV 是微信 2018 年开源的 mmap KV 库，被视频号、抖音、快手等几乎所有头部 App 采用**。它的核心创新是**用 mmap 替代 read/write**——直接把 KV 数据映射到进程的虚拟地址空间。

**源码位置**：`C:\Users\15389\source\MMKV\MMKV\`（30+ 个 .cpp/.h）

### 9.1 MMKV 的设计哲学

```
传统 KV (SharedPreferences / NSUserDefaults):
write(k, v) → [序列化] → 整文件 mmap write → [fsync] → 返回

MMKV:
write(k, v) → [append 到 mmap] → 立刻返回（fsync 由后台线程做）
read(k)   → [内存直接读] → 无 syscall
```

**性能差异**：
- write 速度：**5-10 倍**（省掉整个文件序列化）
- read 速度：**10-30 倍**（无 syscall，CPU cache 友好）
- 跨进程：**1 倍**（因为是 mmap，进程间共享内存）

## 10. MMKV mmap 内存布局与扩容

> **MMKV 的 mmap 文件不是普通文件——它的前 4 字节是实际数据长度，第 5 字节起是 protobuf 编码的 KV 列表**。

### 10.1 文件结构

```
┌──────────────────────────────────────────────────┐
│  [0-3]   actualSize (uint32_t)  实际数据大小       │
│  [4-N]   protobuf-encoded KV list                │
│  [N+1...]   预分配空间（防止溢出）                  │
└──────────────────────────────────────────────────┘
```

**`actualSize`**——记录当前实际用了多少字节。读取时用 `mmap.ptr() + 4` 开始读，读 `actualSize` 字节。

**预分配空间**——MMKV 第一次 mmap 时会预分配大文件（如 8KB），后续 append 在 mmap 范围内。**当 append 超出预分配范围时，重新 mmap 更大的文件**。

### 10.2 扩容策略

```cpp
// 伪代码：append 时检测是否需要扩容
size_t need_size = current_size + delta;
if (need_size > mmap_size_) {
    // 扩容：新大小 = max(need_size * 2, current * 1.5)
    size_t new_size = std::max(need_size * 2, current_size_ * 3 / 2);
    mmap_size_ = new_size;
    mremap(mmap_ptr_, old_size, new_size);  // 内存级扩容
    // 注意：mremap 不修改文件大小，文件大小等后台线程刷盘
}
```

**`mremap` 是 Linux 特有**——它能在不重新分配内存的情况下扩大 mmap 区域，速度极快。**MMKV 扩容时不需要重新分配内存**，只是把映射区域扩大。

### 10.3 多实例（多文件）

```cpp

inline uint32_t hardware_crc32(uint32_t crc, const void* buf, size_t len) {

    buf += 8; len -= 8;
```

## 18. 视频号连麦：SFU + Mesh 混合架构

> **2 人连麦用 Mesh，3 人以上用 SFU**——这是视频号的混合架构。

### 18.1 Mesh（P2P）

```
        主播
       /    \
   连麦者1   连麦者2
   (直接 P2P)
```

**优点**：延迟最低，无中转服务器成本
**缺点**：N 人连麦 = N² 路流，3 人 = 6 路，4 人 = 12 路，CPU/带宽爆

### 18.2 SFU（Selective Forwarding Unit）

```
              主播
                |
              SFU
            /  |  \
         L1  L2  L3
       (选择性转发)
```

**优点**：N 人连麦 = N 路流，CPU/带宽省
**缺点**：SFU 服务器成本 + 1 跳延迟

### 18.3 视频号的选择

| 连麦人数 | 架构 | 原因 |
|---|---|---|
| 2 人 | Mesh | 延迟低、省成本 |
| 3-6 人 | SFU | 平衡 |
| 7+ 人 | SFU + Simulcast | 多人时降低下行带宽 |

**Simulcast**：主播同时推 3 路流（360p/720p/1080p），SFU 根据观众带宽选最合适的一路推。

## 19. 视频号弱网优化：FEC + ARQ + 带宽估计

### 19.1 三种抗弱网技术

| 技术 | 原理 | 适用场景 |
|---|---|---|
| **FEC** (Forward Error Correction) | 发 N 个包 + M 个冗余包，收 N+M 中任意 N 个就能恢复 | 中等丢包（5-15%） |
| **ARQ** (Automatic Repeat reQuest) | 丢包就重传 | 高丢包（>15%） |
| **Hybrid** | FEC + ARQ 混合 | 视频号默认 |

### 19.2 视频号的带宽估计

```cpp
// 伪代码：GCC (Google Congestion Control) 算法
class BandwidthEstimator {
    int64_t last_loss_time_ = 0;
    int64_t last_delay_time_ = 0;
    
    int estimate() {
        // 1. 丢包率
        double loss_rate = (lost_packets_ * 100.0) / total_packets_;
        
        // 2. 延迟变化（jitter）
        int64_t delay = current_rtt - baseline_rtt;
        
        // 3. 决策
        if (loss_rate > 10 || delay > 100) {
            // 网络拥塞，降码率
            bitrate_ = bitrate_ * 0.85;
        } else if (loss_rate < 2 && delay < 30) {
            // 网络良好，升码率
            bitrate_ = bitrate_ * 1.05;
        }
        
        return bitrate_;
    }
};
```

**切换频率**：1 秒 1 次（不能太频繁，会闪屏）。

## 20. 视频号 CDN 调度：多 IP racing 选最优

> **视频号用户在 5G 切 WiFi 时，Mars 的多 IP 竞速机制会自动选新 IP**——这是 MComplexConnect 在生产环境最常被触发的场景。

### 20.1 CDN 选路流程

```
用户点开视频号
    ↓
客户端请求"最近的 CDN 节点"（带经纬度）
    ↓
腾讯云 LIVE 调度系统返回 4-8 个 IP
    ↓
客户端 MComplexConnect 多 IP 竞速
    ↓
选最优的 IP 拉流/推流
```

### 20.2 调度算法

| 因素 | 权重 |
|---|---|
| 地理位置（经纬度） | 40% |
| 实时网络质量（丢包/RTT） | 30% |
| 节点负载 | 20% |
| ISP 归属 | 10% |

**实时网络质量**——通过客户端心跳上报："这个节点我过去 10s 的 RTT 是 50ms、丢包率 0.5%"。
